# axeyum vs z3 — method

> **Kind:** reference · **Status:** maintained

A layered benchmark comparing the **axeyum** (pure-Rust, in-process) and **z3**
(libz3 via the `z3` crate) backends on the exact solver workload Glaurung's
symbolic-execution engine produces. This file is the **method**. The numbers are
the files beside it in `results/`, regenerated by one script, and they carry
their own provenance stamp rather than being quoted here.

## Thesis under test

Symbolic execution of binaries issues **very many small, mostly-independent
QF_BV queries**, and then — through the warm/incremental path — **many related
queries that share long assertion prefixes**. Four claims follow:

- **C1 Correctness.** axeyum returns the same verdicts as z3, and as
  construction-truth, on Glaurung's query distribution.
- **C2 Cold speed.** On small one-shot formulas axeyum has no per-call
  FFI/context floor to pay; the edge should shrink as formulas grow.
- **C3 Warm speed.** Retained incremental state is the structural lever that
  decides whether real driver streams are a net win.
- **C4 Deployability.** Pure Rust, no libz3, correct at every width, DRAT
  proofs, no crashes or hangs at scale.

## Tiers

Layered bottom-up so a reader can see *where* any aggregate number comes from.

| Tier | What it measures | Harness | Isolates |
|---|---|---|---|
| 0 | solver primitives — every QF_BV operator × width, sat and unsat | `examples/axeyum_bench_primitives.rs` | per-operator blast cost, and verdict correctness |
| 1 | formula families — 20 path-condition-shaped formulas | `examples/axeyum_diff.rs` | realistic small-formula shapes |
| 1b | mechanism sweep — one always-sat family across width × conjunct count | `examples/axeyum_sweep.rs` | the fixed-overhead floor versus bit-blast growth |
| 2 | warm versus one-shot — a narrowing path condition re-checked per step | `examples/axeyum_incremental.rs` | the incremental-reuse lever (C3) |
| 3 | real driver streams — full `ioctlance` analysis under shadow-diff | `examples/ioctlance.rs` | the production query distribution |

All five are declared in `Cargo.toml` with `required-features`; tiers 0–2 need
`solver-z3,solver-axeyum`, tier 3 needs at least `symbolic`.

## Method discipline

These five rules are the reason the harness exists; a comparison that drops any
of them has produced a wrong answer here before.

- **Shadow-differential for tiers 1 and 3.** `GLAURUNG_SHADOW_DIFF=1` runs *both*
  backends on every query with **z3 authoritative**, so the query stream and path
  lineage are identical across runs and the two per-backend times are
  apples-to-apples on the same work.
- **Construction-truth grading for tier 0.** Each case's verdict is known by
  construction — a SAT case carries an explicit witness, an UNSAT case is
  `t == v ∧ t == v^1`. Both backends are graded against that truth, so no solver
  is trusted as the oracle and a wrong verdict from *either* side is caught, not
  merely "they disagreed".
- **Instrument unknown and error counts per backend, always.** A "faster" number
  that coincides with dropped work is not a speedup. An early ad-hoc sweep
  reported inflated driver speedups because hundreds of queries were fast-
  *erroring* on a concat-width bug rather than solving; the whole 12–29× claim
  that came out of that was retracted. Tier 3 reports unknown-split counts, not
  only verdict agreement.
- **One-shot means one-shot.** Tiers 0, 1 and 1b build a fresh solver per
  `check`, matching `Solver::check`'s contract. Tier 2 is the only tier that
  exercises the warm path, and it says so.
- **Say which build.** Everything here is `--release`. A number from a debug
  build is not comparable to one from a release build.

## Running it

```sh
export TMPDIR="$HOME/.cache/glaurung/tmp"

# fast drivers only (a few minutes)
bench/axeyum/run_benchmark.sh --fast

# add the large kernel drivers tcpip/dxgkrnl (minutes each)
bench/axeyum/run_benchmark.sh --full-drivers
```

The script builds with `FEATURES="solver-z3,solver-axeyum"`, runs the five
harnesses in order, and writes `results/` plus a fresh `results/provenance.txt`.
It grades both backends at every width and exits nonzero on any wrong verdict.

## Provenance format

Every run stamps `results/provenance.txt`; a result file without a matching
stamp is not evidence.

```
date_utc:     <ISO-8601 UTC>
glaurung_rev: <full SHA>
axeyum_rev:   <full SHA>
host:         <uname>
cpu:          <model>
rustc:        <version string>
```

## The checked-in results are a snapshot, and they have drifted

`results/` holds an immutable run whose `provenance.txt` records
`axeyum_rev: 1cc19181`. **`Cargo.toml` now pins axeyum at `c38a9515`**, so the
checked-in numbers predate the current solver. That run also predates the
wide-constant fix in the z3 adapter (`4ae96cfd`), which means its head-to-head
timing was scoped to ≤64-bit widths; the current harness treats both backends as
required-correct at 128 bits too. Rerunning replaces the result files and
restamps the provenance. Compare a `results/` number against a current claim only
after checking that both revisions match.

## Threats to validity

- **Single-run timing.** Median-of-N within a harness, but one process per tier:
  strong signal, not variance-gated. The repeated, RSS- and variance-gated
  contract is `tools/axeyum/lineage_gate.py`; use that for regression gating.
- **z3 as Glaurung uses it** — one fresh solver per call through the `z3` crate.
  That *is* the real integration, but a z3 embedding that reused a context would
  show a smaller floor. The comparison is scoped accordingly.
- **Tier 3 is z3-authoritative**, which isolates solver cost fairly but means the
  query stream reflects z3's model choices.
- **Tiers 0–2 are author-constructed.** They explain mechanism and correctness;
  every real-workload claim rests on tier 3.
- **Bitwuzla is not in this benchmark.** The pinned `solver-bitwuzla` cell is a
  separate, topology-equivalent control with its own preregistration
  requirements — see `docs/decisions/solver-031-pinned-bitwuzla-measurement-cell.md`.
