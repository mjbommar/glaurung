# Trusted minisign public keys

> **Kind:** reference · **Status:** maintained

Every `*.pub` in this directory is a key whose signature over a signature-set
manifest this installation will accept. `glaurung.sigs.client.load_trusted_keys`
reads the whole directory, and `glaurung sigs status` prints the key ids.

## `glaurung-sigs.pub` — the production key

Key id `25655013D3F68BC1`, generated by the maintainer on their own machine
with stock minisign, **password-protected**:

```bash
minisign -G -s glaurung-sigs.key -p glaurung-sigs.pub
```

**Its secret half never leaves the maintainer's machine and is never read by
any tool in this repository.** `glaurung.sigs.minisign.SecretKey` only parses
minisign's password-less form — correctly, since decrypting a
scrypt-protected key needs a passphrase no automated tool should ever ask
for or see. This is why `tools/publish_signature_set.py` never signs a real
release itself: it writes `manifest.json`, prints the exact command below,
and only *verifies* the `.minisig` the maintainer produces by hand.

To sign a release the maintainer runs, interactively (minisign prompts for
the passphrase on its controlling terminal):

```bash
minisign -Sm <out>/manifest.json -s <path to glaurung-sigs.key> \
    -t "<the manifest's canonical trusted comment, printed by the publish tool>"
```

`tools/publish_signature_set.py` prints this exact command (with the real
paths and values filled in) every time it builds a release, and refuses to
proceed to the S3/GitHub publish steps until it is given the resulting
`<out>/manifest.json.minisig` via `--signature` and that file verifies
against a key in this directory with a trusted comment naming the same set
version and serial. See "Publishing a release, step by step" in
[`docs/reference/signature-distribution.md`](../../../docs/reference/signature-distribution.md).

### Rotation

A new key ships beside the old one for a release or two — both verify, then
the old one is deleted, so a client that has not upgraded yet still verifies
and a client that has already upgraded accepts the new key without a flag
day. To rotate: add the new `.pub` here first (commit it), keep the old
`.pub` in place until every manifest it ever signed has passed its
`valid_until`, then delete the old `.pub` in a later commit.

exercise a locally-generated, locally-trusted key. A shipped client trusts
only the production key above.

## Why a directory and not one embedded key

Key rotation has to be a non-event. A new key ships beside the old one for a
release or two, both verify, then the old one is deleted — so a client that
has not upgraded yet still verifies, and a client that has upgraded already
accepts the new key. A single key compiled into the binary makes rotation a
flag day, where every unupgraded client breaks the moment the key changes.

## What a key here can and cannot do

It can attest that a manifest — the set name, version, monotonic serial, and
every blob's sha256 — came from whoever holds the corresponding secret. It
cannot attest anything about the *contents* of a blob beyond its digest, and
it is not a statement about the licence or provenance of the inputs; those are
per-blob fields in the manifest and are covered by the same signature only in
the sense that they cannot be edited without breaking it.

## Never commit a secret key

A `.key` file under `data/sigs/` is a leaked signing key, not a test fixture.
`python/tests/test_sigs_minisign.py::test_no_secret_key_was_ever_committed`
fails if one appears.
