## Raise phi-copy coalescing past the 46 % width-ambiguity refusal rate

`value_number::coalesce_phi_copies` removes ~40 % of out-of-SSA copies.
Measured on stripped ubuntu `grep` (15 functions with phis, 4,033 merge
attempts): 36 % merged, 7 % refused for INTERFERENCE, **46 % refused for WIDTH
AMBIGUITY**, 11 % already in the same class.

Interference is doing its job; width is the binding constraint, and it is an
artifact rather than a real conflict. `definition_widths` is keyed by NAME, so a
kept-bare name (`rax` held bare because it reaches a return, or a structural
frame register) collapses every definition of that name into one entry. The
coalescer cannot then attribute a width to a phi edge from such a name and marks
the phi ambiguous. It already special-cases a bare name with exactly one
definition; the remaining refusals are names with several.

**Fix:** give definitions widths per DEF SITE, not per name.
`value_number_with_definition_widths` already walks `(block, instr)` pairs and
has the raw `lf` in hand, so it can build `HashMap<InstrAddr, u8>` alongside the
existing map without changing what downstream consumers see.

**Do NOT** relax this by treating a live-in parameter (zero definitions) as "no
opinion". That was tried and reverted: it let the loop-carried phi in
`11_call_shapes:gcc:O2:call_chain_in_loop` join the entry parameter's class, and
every iteration called `signed_step(seed)` instead of `signed_step(v)`. The
fixture harness caught it (655/656); the comment in `class_widths` records this.

## Normalise a wrapped 32-bit array index instead of printing its unsigned representative

DIAGNOSED PRECISELY, not fixed. Reproduce with `gcc -m32 -O0` on
`tests/decompiler_fixtures/src/30_finite_difference.c`, `heat_step_1d`. Source
`source[i - 1]` recovers as `var13 = arg1[(local_14 + 0x3fffffff)];`

**This is not a wrong value.** The arithmetic is exact modulo 2^32 — for i = 1,
`(1 + 0x3FFFFFFF) * 4 = 2^32 = 0`, i.e. `source[0]`, correct. The defect is that
we print the *unsigned representative* of a wrapped value rather than its signed
equivalent. The byte offset is −4 = `0xFFFFFFFC`; dividing by the 4-byte element
size gives `0x3FFFFFFF`, a legitimate unsigned quotient and the wrong reading.
With element size S and 32-bit pointers, index arithmetic is mod 2^32/S, so the
constant should be normalised into [−2^31/S, 2^31/S): `0x3FFFFFFF − 0x40000000 =
−1`, giving `arg1[local_14 - 1]`.

Why it matters twice: unreadable (a billion-element index into a 16-element
array), **and it breaks the LP64 rebuild** — at 64 bits there is no wrap, so the
recompiled code indexes 4 GB out of bounds. `tools/arch_roundtrip.py` marks these
lanes ABI-incomparable for exactly that reason, which is why no behavioural gate
catches it.

The index reaches the renderer already folded, so `try_array_index` /
`scaled_index` in `src/ir/ast.rs` only extract it — the factoring of `k*S + C`
into `(k + C/S)*S` happens upstream. **Find that fold first**; normalising at the
fold also helps const-folding and comparison. The normalisation is valid only
when the target pointer width is 32 bits, so that site needs the pointer width in
scope. Do not apply it unconditionally — on LP64 `0x3FFFFFFF` is a genuine index.

## C++ recovery, all four architectures — 40–50 % off the control lane

`g++-arm-linux-gnueabihf` and `g++-aarch64-linux-gnu` (15.2.0-16ubuntu1cross1)
were installed 2026-08-03, which automatically un-declared the
`10_cpp_runtime_shapes` gap in `tools/arch_roundtrip.py` (`detect_unsupported`
probes the toolchain rather than reading a list). No code change was needed.

```
x86_64   5/5 at each of O0/O2   (control)
i386     1/5 O0,  4/5 O2
aarch64  3/5 O0,  2/5 O2
armv7    0/5 O0,  4/5 O2
```

`cpp_exception` fails on all three non-control lanes at both O0 and O2 — the
largest C++ cluster and the obvious first target. `armv7:O0` failing all five,
against 4/5 at O2, says that is a **-O0 shape problem, not an Itanium-ABI
problem**. 40 mangled member functions per lane remain `structural` (no execution
verdict), unchanged from x86-64.

## Six ARMv7 `getent` functions recover no format strings that angr finds

In `strip_getent_arm-v7`, angr recovers format strings we do not at 0x13c4,
0x14b0, 0x14e0, 0x162c, 0x170e, 0x1850 (`"%-16s"`, `"%s:%s:%u"`,
`"%-15s %-6s %s\n"`, `"# unknown"`). Our 0x13c4 calls only `ntohs` and
`sub_134c` and contains no printf-family call at all — so the **function extent
or call recovery** differs, not the string pass.

**NOT adjudicated, deliberately.** Stripped ARMv7 is Thumb; stripping removes the
`$a`/`$t` mapping symbols, and llvm-objdump decodes the region as ARM producing
nonsense (`movwlt pc, #0xf33` at 0x1444). `tools/extbench/callcheck.py` already
excludes 32-bit ARM from its correctness probe for this reason. Deciding whether
our extent or angr's is correct needs a reference that can distinguish Thumb from
ARM — an unstripped twin with mapping symbols, or a decode driven from
`.ARM.exidx`. **Do that first; do not "fix" this against an unreliable
reference.**

This is the bulk of the remaining ARMv7 string gap (0.419/fn vs angr 1.310) and
it is **not** in the string layer, which is verified correct on all three
architectures.

## x86 lifter: `zf` is computed over the untruncated parent register

`test edi, edi` lifts as `t = rdi & rdi; zf = (t == 0)` — the zero flag over the
UNTRUNCATED 64-bit parent while `sf` narrows to 32 bits. The two halves of a
`jle`/`jg` flag pair therefore disagree on cast depth, and
`bool_guard::recover_inclusive_comparisons` correctly REFUSES to merge them:
doing so would assert `rdi == 0 <=> sext32(edi) == 0`, unprovable from the AST.

Consequence: ~30 unmerged flag pairs remain at -O2, each emitted as
`((arg0 == 0) | ((long)(arg0) < 0))` instead of the `<=` / `>=` the source had.

**Fix:** narrow `zf` to the encoded operand width at the point of use, the way
`sf` already does — the same class of change as the existing
`unsigned_cmp_value` / `signed_cmp_value` width statements in `lift_x86.rs`.

**RISK:** touches flag semantics on EVERY x86 binary. Measure on the full gate
set; the control lane at 328/328 is non-negotiable. A wrong narrowing silently
changes which branch is taken — the canary-check defect (`subs` comparing the
already-updated register) is the precedent for how bad that gets.

Unblocks merging the -O2 half of the flag pairs, and relaxing `bool_guard`'s
`saw_byte_view` gate so the one genuine compiler-fused guard in the fixture
corpus (`01_conditional_polarity:gcc:O2:sc_mixed`) can be recovered as `&&`.
